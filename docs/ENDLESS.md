## Implemented ownership and recovery

`GeneratedGameBatch.prepare` uses `@concurrent` value generation with a reproducible SplitMix64 seed. Each batch supplies eight descriptors; replenishment starts with four remaining cards. Production chooses a new session UUID and seed once. Issue #106 shuffles games only, then carries five-game/news cadence across batches while preserving appended history. The dedicated Debug route orders seed104 batches for deterministic native checks.

`FeedComposition` retains append-only cards, descriptors, known IDs, and completed pure rule snapshots. These lightweight values grow with the session so revisits preserve identity, configuration, and completed results; total session memory is not constant. Heavy controllers/runtimes and hosted native pages are limited to previous/current/next. Eviction archives completed Sudoku board/selection, Memory rules, solved Chess attempt, or Bubble game/aim/feedback. It permanently retires the old runtime before releasing its adapter. Restoration creates a fresh invisible runtime with the trusted completed attempt identity and binds one new owner. Skipped unfinished cards return to the same frozen challenge. Bubble Replay resets that frozen configuration and removes the old completion if subsequently skipped unfinished.

Issue #106 separates each news appearance from its unchanged source snapshot. Initial and appended candidates validate actual appearance/game IDs before commit; an imported source ID resembling a game no longer removes that generated game. No arbitrary source-ID prefix is reserved. Cadence partial count, cursor, and ordinal advance only with accepted additions. A session/request-owned task gates batch results and errors after every suspension; background, modal absence, retirement, or replacement cancels it. A failed current generation retains history and offers an accessible Retry games action. Retrying prepares the same next sequence. Generation never starts play or automatically changes the selected card.

The historical mini Sudoku generator transforms a solved grid and considers each of its 16 clues once. Child #170 changes normal production to standard 9×9 puzzles with at most 12 editable cells, accepting each removal only after exhaustive uniqueness proof. The batch consumes historical mini draws for neighboring-game/shuffle compatibility, then generates standard values from a separate stable seed/index stream. Dedicated Debug endless regressions explicitly select mini; the format remains frozen per descriptor, including reset and completed restoration. Memory generates exactly two of each of six symbols and freezes the result. The initial #104 Bubble generator supplied easy one-shot challenges. Owner-authorized #137 supersedes that production default with eight original compact two-row patterns, color permutations and horizontal reflection. Three independent ceiling color groups require three clearing actions; each selected three-shot witness is replayed through real rules. Preparation tries at most four candidates with three shot evaluations each, followed by one independently replayed three-shot fallback (at most 15 evaluations). No recursive search, larger board, difficulty tier or score is introduced. Chess positions remain the two validated bundled puzzles, not newly generated positions.

The native pager compares adjacent-window membership as well as selection. It delays window rebuilding/recentering during tracking, drag, deceleration, or a requested animation, then refreshes after settlement. Existing gesture arbitration, accessible navigation, and system Reduce Motion remain applicable.

`NewsImportModel` captures a `NewsReplacementRequest` before its first read/load await. The session verifies the origin before/after async candidate generation. A prepared candidate then acquires a main-actor lease across save and adoption; competing replacement cannot commit during that boundary. Failed/canceled/stale preparation or failed persistence keeps saved news/current feed and releases the lease. After successful durable save, news and feed synchronously adopt without another cancellation check, throw, or suspension. Other finite Debug routes retain their existing contracts and original fictional fixtures. The endless native route uses an isolated `EndlessNewsTests` store and no real captures.

## Bidirectional scrolling #216

The owner approved newly generated history above the initial card and endless scrolling in either direction. Normal startup seeds both sides, selects the first forward game, and replenishes at four remaining cards on either edge. Independent UUID namespaces and nonnegative sequence counters keep challenge IDs distinct. Backward batches are stored in reverse outward order, with news boundaries aligned to retain five games between articles across the starting seam. No history is persisted between launches.

Preparation completing during a physical swipe is held until settlement; inserting cards preserves selected identity and its existing attempt, without a reset or streak event. The three-dot menu omits Previous/Next; named pager accessibility actions use ordinary settled programmatic requests. Existing cancellation, retry, bounded heavy adapters and completed restoration remain required. Verification belongs to the owning PR.

## Successful auto-continue #84

Normal sessions enable a three-second neutral3–2–1 circular timer after a new successful visible attempt. Tap it to disable auto-continue for the session; the More options toggle reenables it for future wins. Countdown chrome has a constant44-point slot and Reduce Motion uses numeric ticks without ring animation. A session-owned cancelable task validates its request after every tick. Composition uses the existing single success observer for both participation and countdown.

Manual paging, background, modal presentation, leaving, session replacement and disable cancel advancement. Completed revisits, news, losses and stale callbacks do not start timers. At expiry, the view validates originating card/attempt and eligibility and makes one ordinary native page request; unavailable next cards retain the result with no repeated movement. Automatic movement never counts as a physical swipe for the streak. Deterministic countdown gates and native timer/direct paging journeys verify these boundaries; no release is implied.
