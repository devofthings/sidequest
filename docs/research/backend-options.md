# Phase-two backend options

Research date: 2026-10-03. Issue: [#18](https://github.com/devofthings/sidequest/issues/18). Status: **research complete; provider recommendation proposed**.

The user confirmed accounts, synced preferences, high scores, and shared leaderboards for phase two. Centrally managed news is unconfirmed. The private MVP remains local, uses manually imported news, and resets skipped unfinished games. No services were provisioned or billing enabled.

## Proposed recommendation

Start phase two with **Firebase Authentication and Firestore**, subject to user review. The user's Firebase experience, supported Swift integration, and built-in offline sync make it a practical fit for preferences. Simple per-game leaderboards fit; sophisticated ranking would strengthen Supabase's case. This is a judgment based on the capabilities below, not an accepted provider decision. Avoid introducing a backend SDK during the MVP.

If centrally managed news becomes necessary, Firebase/Supabase dashboards could support an initial catalog, followed by an editorial adapter/tool. That is a separate requirement; none provides content rights or an editorial workflow automatically.

## Current costs and limits

Amounts are USD before taxes, not guaranteed future prices or a quoted bill.

- **Firebase Spark:** no payment method needed. Firestore Standard includes 1 GiB data, 50,000 reads/day, 20,000 writes/day, 20,000 deletes/day, and 10 GiB network egress/month. Basic non-phone Auth is available; Identity Platform includes 50,000 MAU before paid-tier overages. [Pricing](https://firebase.google.com/pricing). Phone verification needs Blaze; Spark email-link sign-in sending is only five emails/day. Identity Platform Spark also limits Tier 1 usage to 3,000 daily active users. [Auth limits](https://firebase.google.com/docs/auth/limits).
- **Firebase Hosting:** static website/assets include 10 GB storage and 10 GB transfer/month. Spark sites can stop serving after the transfer allowance/grace period. This can host a landing page/privacy page, not distribute an iPhone app. [Hosting quotas](https://firebase.google.com/docs/hosting/usage-quotas-pricing). **App Hosting** is a different dynamic-web service requiring Blaze and underlying Cloud billing. [App Hosting costs](https://firebase.google.com/docs/app-hosting/costs). Deployed **Cloud Functions** require Blaze even with no-cost allowances (pricing lists two million invocations/month; compute/network limits also apply). [Functions setup](https://firebase.google.com/docs/functions/get-started), [pricing](https://firebase.google.com/pricing). Cloud Storage for Firebase also requires Blaze as of February 3, 2026; new-bucket free usage depends on eligible US regions. Preferences do not require file storage. [Storage requirements](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024).
- **Supabase Free:** two active projects; 50,000 MAU, 500 MB database/project, 1 GB storage, 5 GB egress plus 5 GB cached egress, 500,000 Edge Function invocations, and two million Realtime messages/month. Free projects pause after one week of inactivity. Pro starts at $25/month with one project included; additional projects start at $10/month. [Pricing](https://supabase.com/pricing). Email auth for users requires custom SMTP: default delivery is limited to team addresses and two emails/hour. Sender costs are separate. [SMTP](https://supabase.com/docs/guides/auth/auth-smtp). Edge Functions are included; a general frontend website needs separate hosting.
- **CloudKit:** private records consume each user's iCloud quota. Apple's public page advertises scaling up to 1 PB, but does not establish a flat free public quota or a per-request price; verify container limits before relying on public leaderboards. [Private quota](https://developer.apple.com/documentation/cloudkit/ckcontainer/privateclouddatabase), [CloudKit overview](https://developer.apple.com/icloud/cloudkit/). Apple Developer Program membership/distribution costs are separate from backend usage. [Membership](https://developer.apple.com/programs/whats-included/).

Budget alerts do **not** stop Firebase services. Current Firebase docs also describe service-specific spend caps for Functions, App Hosting, Extensions, and AI Logic; these are not a global Firestore/Auth cap. [Cost controls](https://firebase.google.com/docs/projects/billing/avoid-surprise-bills). Supabase Pro's Spend Cap covers selected usage, excluding compute and several add-ons; Free incurs no usage charges but can be restricted. [Cost controls](https://supabase.com/docs/guides/platform/cost-control).

**Illustrative workload:** 1,000 daily users, one preference fetch/update each, and one 20-entry leaderboard fetch each means approximately 21,000 document reads/day and 1,000 preference writes/day before scores, retries, listeners, and indexes. This fits listed Firestore operation allowances; 10,000 daily users doing the same exceed them. At 1 KiB/entry, leaderboard responses alone are roughly 0.6 GB/month for 1,000 daily users. Actual billing also depends on auth choice, stored history, regions, indexes, protocol overhead, and reconnects.

## Leaderboards and hexagonal boundaries

Use per-game, difficulty/puzzle/rules-version metrics; a universal score is an unresolved product choice. Firestore supports ordered limited top-N queries, while exact global ranks require additional work. [Query API](https://firebase.google.com/docs/firestore/query-data/order-limit-data), [leaderboard designs](https://firebase.google.com/codelabs/build-leaderboards-with-firestore). Supabase SQL functions can expose rankings using PostgreSQL window functions. [RPC](https://supabase.com/docs/guides/database/functions), [ranking functions](https://www.postgresql.org/docs/current/functions-window.html). CloudKit offers public record queries; richer ranking and trusted validation need separate design. [Queries](https://developer.apple.com/documentation/cloudkit/ckquery).

Ownership rules can restrict submissions, but cannot prove a client honestly played. Decide between casual self-reported scores and validated outcomes before promising fair competition. Limit/paginate reads and avoid broadcasting entire boards after every score.

Keep SDK models outside the pure Swift core. Add account, preference-sync, and score/leaderboard ports only as phase-two use cases need them; wire concrete adapters at the composition root. Define provider-neutral IDs, conflict behavior, failed/offline submissions, account deletion, and neutral exports. Ports make migration manageable, not free.

Next: review Firebase as the proposed default; specify login methods, sync conflicts, score trust, and bounded ranking queries before a provider ADR. Revisit Supabase if complex rankings/relational reporting dominate, or CloudKit if iCloud-only private sync becomes sufficient. Recheck prices before provisioning. No live backend or SDK integration was tested.
